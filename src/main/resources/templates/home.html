方式三：设备授权模式 (Device Code / RFC 8628)

            
适用于 TV、CLI、物联网设备等没有浏览器的场景。


            
完整流程

            
    
                
  1. 获取 device_code — 点击下方按钮，DUCA 返回 device_code、user_code、verification_uri
    2. 
                
  2. 用户在手机/其他设备上打开验证链接，输入 user_code 或直接访问完整链接完成授权
    3. 
                
  3. 轮询令牌 — 设备持续轮询 token endpoint，直到用户确认授权后返回 access_token / refresh_token
    4.

方式二：授权码 + PKCE (Proof Key for Code Exchange)

            
PKCE 是授权码流程的安全增强，防止授权码拦截攻击。客户端生成随机 code_verifier，用 SHA256 哈希后得到 code_challenge。授权时发送 challenge，换令牌时发送 verifier 自证身份 — 不需要 client_secret。


            
完整流程

            
    
                
  1. 生成 PKCE 参数 — 点击下方按钮生成 code_verifier 和 code_challenge
    2. 
                
  2. 发起授权请求 — 携带 code_challenge 和 code_challenge_method=S256 跳转 DUCA 授权页
    3. 
                
  3. 用户登录授权 — DUCA 验证用户身份后，带 authorization_code 重定向回回调地址
    4. 
                
  4. 用 code_verifier 换令牌 — 回调页自动用 code + code_verifier 到 token endpoint 换取 access_token / id_token
    5. 
            


            

                
                

                    
                    
                

            

            

            

                
                

                    
                    
                

            


            
            

                callback 地址: /api/auth/pkce/callback (已配置为 permitAll)

                回调页将自动从 sessionStorage 读取 code_verifier 并换取令牌。

方式十：PAR (Pushed Authorization Request / RFC 9126)

            
将授权参数（scope、redirect_uri 等）通过后端 POST 推送到 DUCA 的 PAR 端点，获取一个短时效的 request_uri。然后用这个 request_uri 发起授权 — 请求参数不会暴露在 URL 中，且支持预校验。


            
完整流程

            
    
                
  1. 推送授权参数 — 将 redirect_uri、scope 等 POST 到 DUCA PAR 端点
    2. 
                
  2. 获取 request_uri — DUCA 返回 request_uri（形如 urn:ietf:params:oauth:request_uri:xxx）和 expires_in
    3. 
                
  3. 发起授权 — 跳转 authorize 端点，只携带 request_uri 和 client_id，无需其他参数
    4. 
                
  4. 用户授权 → 标准 code 回调
    5. 
            


            

            

            

                

                

                

                    
                    

                        
                        
                    

                

                在新窗口打开 PAR 授权链接 →
            

            

        

    


    
    

        

            
方式十一：Token Exchange (令牌交换)

            
用已有令牌换新令牌，可指定不同的 audience 和更窄的 scope。适用于微服务委托调用。

            

            

            
            

        

    


    
    

        

            
方式九：DPoP (Demonstration of Proof-of-Possession / RFC 9449)

            
将 Access Token 绑定到客户端非对称密钥对。每次 API 请求都需要携带 DPoP Proof JWT（用私钥签名的 JWT），服务端验证后确认请求者持有私钥 — 即使令牌泄露也无法冒用。


            
完整流程

            
    
                
  1. 生成 RSA 密钥对 — 使用 Web Crypto API（浏览器内，私钥不离开客户端）
    2. 
                
  2. 构建 DPoP Proof JWT — 包含公钥 jwk + 请求绑定 claims（htm/htu/iat/jti）
    3. 
                
  3. 发送 DPoP 绑定请求 — 在 DPoP HTTP Header 中携带 Proof JWT，同时携带 access_token
    4. 
                
  4. 验证 — 服务端验证签名、重放检测、令牌绑定（ath claim）
    5. 
            


            
            


            

                

                

                
            


            

            

        

    


    
    

        

            
统一退出 (RP-Initiated + Back-Channel + 挤掉)

            
DUCA 统一退出包含三种机制：RP-Initiated Logout（前端主动退出）、Back-Channel Logout（服务端通知退出）、Concurrent Session（被挤掉）。


            
退出流程架构

            

                

                    
用户主动退出

                    
    
                        
  1. 浏览器 → DUCA /logout
    2. 
                        
  2. DUCA 清除认证服务器会话
    3. 
                        
  3. DUCA → POST logout_token 到所有客户端的 backChannelLogoutUri
    4. 
                        
  4. DUCA → 302 重定向到 post_logout_redirect_uri
    5. 
                        
  5. 客户端解析 JWT，reason=manual_logout
    6. 
                        
  6. 客户端 sessionRegistry.getAllSessions() → expireNow()
    7. 
                        
  7. 前端轮询 SessionMonitor → 检测 401
    8. 
                        
  8. 弹出通知 "您已退出登录"
    9. 
                    

                

                

                    
被挤掉（新设备登录）

                    
    
                        
  1. 用户 B 在新设备登录同一账号
    2. 
                        
  2. DUCA expireNow() 旧会话
    3. 
                        
  3. DUCA → POST logout_token 到所有客户端的 backChannelLogoutUri
    4. 
                        
  4. 客户端解析 JWT，reason=concurrent_login
    5. 
                        
  5. 客户端 sessionRegistry.getAllSessions() → expireNow()
    6. 
                        
  6. 前端轮询 SessionMonitor → 检测 401
    7. 
                        
  7. 弹出通知 "您的账号已在其他地方登录"
    8. 
                    

                

            


            
1. RP-Initiated Logout（前端主动退出）

            
Spring Security 通过 OidcClientInitiatedLogoutSuccessHandler 实现，退出后 DUCA 重定向到 {baseUrl}/logged-out。

            

            
2. Back-Channel Logout 回调信息

            
DUCA 服务端通过 POST /duca/backChannelLogout（permitAll）发送 logout_token JWT，客户端解析后失效本地会话。

            
回调端点状态：已配置 ✓

            
            


            
3. 模拟 Back-Channel Logout（Demo 仅演示）

            
点击下方按钮模拟 DUCA 发送 back-channel logout 通知（concurrent_login 或 manual_logout）。当前会话将被立即失效，前端 SessionMonitor 检测到 401 后弹出通知。

            

                
                
            


            
4. Session Monitor 状态

            
Session Monitor 每 30 秒轮询 /api/session/check，同时拦截所有 AJAX 的 401 响应检测 session_expired_by_concurrent_login。

            
状态：● 运行中
